# 掃描強化設計（目標：存進字典的單字不出錯）

2026-11-26。使用者要求：「掃描進去的單字絕對不會出錯」。

## 結論

沒有任何單一辨識引擎能保證零錯誤。查過 2026 年的公開評測：印刷文字上，Azure Document Intelligence 約 96%，GPT-5、Gemini、Google Vision、Textract 約 95%；PaddleOCR-VL-1.5 在 OmniDocBench 得 94.5；沒有一份評測直接涵蓋「英文＋繁體中文單字書」。所以做法不是換一個更強的引擎，而是**讓錯誤進不了字典**：

> 一筆條目只有在「兩個互相獨立的引擎讀出完全相同的內容」或「使用者對著原圖裁切確認過」之後，才能存入字典。

## 2026-11-26 更新：不使用付費 API

使用者要求辨識引擎不可消耗他的 token／API 額度。預設流程改為兩個免金鑰、在瀏覽器本機執行的引擎：PP-OCR（主）＋tesseract.js（複核），條目結構化改由規則式版面解析器完成；不加 Gemini API；Claude API 引擎收進預設關閉的進階選項。以下流程中的引擎 A／B 以此為準，其餘把關（逐字比對、詞表、原圖裁切確認、存入門檻）不變。

## 實作現況（2026-11-26）

- 主引擎：PP-OCRv6 small（ONNX＋onnxruntime-web，瀏覽器本機執行，第一次下載約 44 MB）。複核：tesseract.js（約 9 MB）。都免金鑰，下載後快取、可離線。
- 合成書頁測試（26 筆、1467 字元）：PP-OCR 字元正確率 100%、tesseract 93.12%；故意改錯的 4 筆與自然發生的 6 筆錯誤全部被攔下，沒確認就存入會被擋。
- 已知限制：兩個引擎可能犯同一種錯（實測曾同時把 `pick up` 讀成 `pickup`，由規則檢查攔下）；規則攔不到的同向錯誤仍可能通過。測試圖是合成的，真實手機照片還沒驗證。
- Claude API 引擎保留但預設關閉、未實測；沒有做 Gemini。
- 以下「流程」是原始設計，引擎 A／B 以本節為準。

### 真實手機照片（2026-11-26 實測：課本單字頁 4 張，31 筆）

- 照片的文字列是斜的、而且往下越歪越多（扇形），還有書頁彎曲。原本只靠手拉四角，沒有自動校正 → 改前 23 筆裡沒有一筆可用。
- **自動拉平**（`src/scan/deskew.js`，兩個引擎共用）：把墨水橫向連成文字列 → 量每一條的角度 → 擬合成位置的二次斜率場 → 沿著斜率場把每一列拉平（x 不動，只重新對應 y）。平的頁面不動。
- **PP-OCR 沿中心線拉直**（`ppocr-core.js`）：偵測到的區塊比字高明顯高時（長而歪、或彎曲），沿每一欄的中心線把那一列拉直再辨識。
- **字典式版面**（`parse.js` 的 `parseDict`）：左欄編號單字＋音標、右欄「▶ 詞性 中文 英文解釋」＋「• 例句」。分隔線用「詞性＋中文」列的左緣擬合（斜線）；單字和區塊依高度動態規劃配對；右欄沒有單字的區塊是同一個字的另一個意思（併成一筆、要人工確認）；手寫筆記只有同字根、而且旁邊沒有中文的才當候選，印刷的單字（有編號或下一列有音標）優先。隔壁頁、旁邊講義、頁首標題算頁首頁尾，不逼使用者處理。
- **簡繁**（`s2t.js`）：PP-OCR 會把繁體讀成長得像的簡體（羨→羡、滿→满），整頁不是明顯的簡體書時換回繁體（只換一對一的常用字）。
- 結果：PP-OCR 31／31 筆的英文、詞性、中文都對，例句完整；剩下要處理的文字幾乎都是手寫筆記。合成書頁的雙重確認也從 13 筆升到 18 筆（故意改錯的 4 筆照樣攔下）。
- **還不夠好的**：tesseract 在照片上讀得出英文例句，但彩色的中文解釋幾乎讀不出來（換頁面分割模式也一樣），所以照片的條目大多是「只有一邊讀到」，要逐筆對照原圖確認——安全，但比較花時間。可能的改進：讓 tesseract 用中文專用模型重讀詞性那一列。

## 流程

1. **引擎 A：Claude 視覺（`claude-opus-5-5`）** 讀出結構化條目（英文、詞性、中文、例句、例句中的字形、單元、在頁面上的位置）。需要 Anthropic API 金鑰。
2. **引擎 B（獨立重讀）**，依可用性擇一：
   - Gemini API（使用者有 Google 帳號，可在 AI Studio 取得金鑰）：同樣輸出結構化條目，模型家族與 A 不同，錯誤不容易重疊。
   - PP-OCRv6（PaddleOCR，ONNX 版在瀏覽器內執行，免金鑰、免費、可離線）：輸出逐行文字與座標，用來逐字核對 A 的英文與例句。
   - 都沒有時退回 tesseract.js（現有的免費 OCR）。
3. **逐欄比對**：英文、例句做正規化後逐字元比對；中文逐字比對（括號補充另列）。
   - 全部欄位一致 → 綠色「雙重確認」。
   - 任一欄位不同 → 紅色，兩種讀法並列、差異字元標色，旁邊顯示該條目的原圖裁切，使用者點選正確的一邊或自己改。
4. **規則檢查**（沿用並加強原本的核對）：
   - 英文單字查英文詞表（片語逐字查），查不到就標示「可能拼錯」。
   - 例句每個字都查詞表；例句裡找不到該單字的字形就標示。
   - Google 翻譯核對中文（現有規則）。
   - 條目數量比對：兩個引擎讀出的筆數不同時，列出只有一邊有的條目，避免漏字。
5. **存入門檻**：紅色條目沒有逐筆確認就不能存入（原本只是再問一次，現在改成必須逐筆處理或取消勾選）。

## 為什麼這樣能做到「不出錯」

- 兩個不同家族的模型在同一個字上犯同一個錯的機率很低；一致的條目可以信任。
- 不一致的條目一定會被攔下，而且使用者看的是原圖裁切，不是憑印象判斷。
- 詞表與翻譯檢查再攔一次兩邊剛好一致的錯字。

## 實作項目

- `src/scan/engines/`：`claude.js`、`gemini.js`、`ppocr.js`、`tesseract.js`，介面 `extract(canvas) => Promise<Entry[]>`，Entry 可帶 `bbox`。
- `src/scan/consensus.js`：對齊兩份條目（以英文正規化後的編輯距離配對）、逐欄比對、產生差異標記。
- `src/scan/wordlist.js`：英文詞表（常用字約 5 萬筆，壓縮後放 `public/`，用到才載入）。
- 核對清單 UI：每筆顯示原圖裁切、差異並排、狀態（雙重確認／需確認／已人工確認）。
